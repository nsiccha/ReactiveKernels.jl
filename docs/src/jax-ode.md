# JAX ODE solves

This guide continues [JAX runtime and derivatives](jax-runtime.md): how a module solves the native ODE bridges, with diffrax on CPU and one solve per lane on CUDA.

## On every backend

A call of the native ODE bridges `rk_ode_rk45_tol(f, y0, t0, ts, reltol, abstol, maxsteps, args...)` or `rk_ode_bdf_tol` with the same arguments, also inside a plate cell and through a helper such as BayesianRegressionModels' `ode_rk45`, uses [diffrax](https://docs.kidger.site/diffrax/) to integrate across the requested output times. A module that solves an ODE imports `diffrax` (`pip install diffrax`); other modules do not. Emitting needs none of the Julia solver packages the native bridges load. The right-hand side `f(t, y, args...)` is translated like any helper into a nested Python function, and the extra arguments that are runtime values reach it through diffrax's `args`.

- `rk_ode_rk45_tol` is `diffrax.Dopri5()`, the Dormand–Prince 5(4) method of the native `DP5()`. `rk_ode_bdf_tol` is `diffrax.Kvaerno5()`, diffrax's stiff (L-stable implicit Runge–Kutta) method: diffrax has no BDF method, so the stiff solve uses a different method than the native `FBDF()`, with the same tolerances.
- The caller's tolerances are passed unchanged and may be traced (data or parameters). The step size follows a PID controller; outputs come from the solver's dense interpolant, so the native and JAX solves agree to the tolerances, not to the last bit.
- A solve uses the module's float type: a `float_type = Float32` module solves in float32 even with JAX's 64-bit mode on.
- When a solve runs in Float32 with a positive `reltol` below `eps(Float32)` (about `1.19e-7`), the Python module warns once and reports the requested value. For example, `reltol=1e-8` can lead to many small steps. Error control also depends on `abstol` and the state scale. For tighter relative accuracy, export with `float_type = Float64` and enable JAX x64. If the model permits a looser accuracy target, set `reltol` explicitly.
- `maxsteps` limits the accepted steps between consecutive requested outputs, as natively, and may be traced too. diffrax's own static bound on attempted steps is the largest int32, which costs nothing: a gradient keeps 64 checkpoints whatever the bound.
- On CPU, a preliminary integration checks each attempted step and stops at the first non-finite candidate or error estimate. Only its status is used. If every mapped solve completes this check, the output pass uses the ordinary solver. Otherwise the batch uses the solver that isolates rejected trials from differentiation.
- `jax.grad` differentiates the discrete solve (on CPU diffrax's `RecursiveCheckpointAdjoint`, 64 checkpoints a solve; on CUDA forward-mode sensitivities, below), including with respect to the initial and output times, so a gradient's accuracy follows the caller's tolerances, as the native forward sensitivities' does. A backward-solve adjoint such as `jax.experimental.ode.odeint`'s does not: on a seven-state pharmacokinetic model its gradient was about 35 times less accurate at the same tolerances.
- Under `jax.vmap` (a sampler's chains, or a plate's cells) one lane's solve never changes another lane's value: the batch steps until its slowest lane is done and masks the others' extra steps. A lane's gradient is independent of the other lanes only up to rounding. Where diffrax's reverse pass runs (on CPU, and on CUDA with `RK_JAX_ODE_KERNEL=off`), diffrax keeps a batch's backward-pass checkpoints in lockstep, so the lane that needs the most steps decides which steps the backward pass recomputes, and on CUDA XLA's autotuner can compile those recomputed steps to round differently from the forward ones. A lane's gradient then changes in its trailing digits when another lane, valid or failed, needs more steps than it does. The autotuner chooses anew in each process, so one program's gradients also differ between processes, and a point evaluated alone differs from the same point in a batch, by about as much. On a density with a five-state solve in each of 24 plate cells (float64, tolerances `1e-8`) each of these differences was at most `2.1e-4` on gradient entries up to `2e3`, a fifth of the difference between the JAX and native gradients. Compare such gradients with a tolerance, not bitwise. With `XLA_FLAGS=--xla_gpu_autotune_level=0` that experiment gave identical gradients across processes and neighbours. A neighbour that triggers the guarded solver can also change the rounding of a successful lane's gradient on CPU.
- A ragged row of output times solves to the row's last time; its padded rows repeat that time's state, a column `sol[:, j]` keeps the padding, and reductions mask it.
- Invalid inputs (non-finite or non-increasing times, invalid tolerances or `maxsteps`) raise at run time through the module's runtime checks, as the native bridge throws. A row without output times raises nothing.
- An exceeded per-output budget and a failed solve are numerical failures, natively `ReactiveKernels.ODESolveFailure`. From a finite state, a trial with a non-finite candidate or error estimate is rejected and retried with a smaller step. Its discarded stages contribute no gradient. The solve fails if the step size falls below its minimum, if the controller proposes a non-finite step size, or if integration starts a step from a non-finite state. The failure is a `jax.experimental.checkify` check, which leaves every `vmap`, `scan`, `cond` and loop as a value: the functions `jax_source`'s `rejecting` names answer `-inf` for the whole evaluation, and the module's other functions raise. The module's other runtime checks are `checkify` checks too, so the first failure in program order decides, as the native program stops at its first throw: a check on a failed solve's state (a solve continuing from it) neither raises nor hides the failure. ReactiveKernelsPPL's density functions (`log_density` and its parts) are such functions, as its native sampler targets answer `-Inf`. Their gradient there is unspecified.
- A module with an ODE solve therefore needs a JAX whose `checkify` has `checkify.Error.has_error` and differentiates a `custom_vjp` (every diffrax solve) after a check. No JAX release has either yet: with jax 0.12.0.1 such a gradient is wrong or fails (`benchmark/repro_jax_checkify_custom_vjp_control_flow.py`). Branch `jax-v0.12.0.1-checkify` of [nsiccha/jax](https://github.com/nsiccha/jax) carries both, and the module refuses to import without them.

## On CUDA: one solve per lane

On a CUDA device a `rk_ode_rk45_tol` solve runs per lane in one [Pallas](https://docs.jax.dev/en/latest/pallas/) (Triton) kernel. The module selects it per platform (`jax.lax.platform_dependent`), so the same module still runs on CPU as above. Run as XLA's batched while loop, a solve paid on the GPU, per step, a round of kernel launches and a device-to-host check of the loop condition, about fifteen times per step because diffrax also loops over a step's stages, and the batch stepped until its slowest lane was done. On the density above a batched gradient so cost about 0.4 ms per step, and the card was slower than one CPU core.

- Every vmapped call (a plate's cells, a sampler's chains) joins one kernel call (`jax.custom_batching.custom_vmap`). Each lane integrates with its own step sizes. Lanes run 32 to a program, and only those 32 wait for each other.
- The kernel is diffrax's `Dopri5` step for step: the same first step (0.01), tableau, PID control, dense output, per-output budget, retry of a non-finite trial and failure statuses. It takes diffrax's steps up to rounding, and its values agree with the CPU module's to about `1e-11` relative.
- The right-hand side is traced to a jaxpr and evaluated one array element at a time, because the kernel's blocks must have power-of-two shapes. A right-hand side using a primitive this evaluation does not cover (a loop, a sort, an index at a traced position) or one Triton cannot compile in float64 (`erf`, `erfc`, `lgamma`, `digamma`, `round`) warns and keeps diffrax for that solve, with forward-mode sensitivities.
- `jax.grad` uses forward-mode sensitivities: the kernel carries the tangents of the perturbed inputs (parameters, initial state and times) through the steps, and a custom VJP contracts them with the output's cotangent. diffrax stops gradients through step sizes, so these are the derivatives of the same discrete solve as the reverse pass on CPU. There are no checkpoints to recompute.
- `rk_ode_bdf_tol` keeps diffrax's `Kvaerno5` on CUDA, with forward-mode sensitivities (`diffrax.ForwardMode`) instead of the checkpointed reverse pass.
- CPU modules are unchanged: forward-mode tangents cost more there than the reverse pass.
- On the density above (a shared RTX 5060 Ti, whose float64 rate is 1/64 of its float32 rate) a jitted, vmapped value and gradient took 14 ms for one chain (227 ms with diffrax), 45 ms for 64 chains (431 ms) and 78 ms for 256 chains (644 ms). One CPU core takes 5 to 10 ms per chain. A lane's step costs tens of microseconds of float64 arithmetic, so a lane that runs to a large step budget still holds its kernel call for seconds. A sampler that batches chains with `vmap` also evaluates the chains that are done, at their last state: see [Chains under `vmap`](jax-runtime.md#Chains-under-vmap).
- `RK_JAX_ODE_KERNEL` (or the module's `RK_ODE_KERNEL`) is `auto`. `off` keeps diffrax on CUDA too. `interpret` runs the CUDA path on any backend with Pallas' interpreter, as the tests do. Without `jax.experimental.pallas` the module uses diffrax.
