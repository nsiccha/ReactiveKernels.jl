# JAX ODE solves

This guide continues [JAX runtime and derivatives](jax-runtime.md): how a module solves the native ODE bridges, with diffrax on CPU and one solve per lane on CUDA.

## On every backend

A call of the native ODE bridges `rk_ode_rk45_tol(f, y0, t0, ts, reltol, abstol, maxsteps, args...)` or `rk_ode_bdf_tol` with the same arguments, also inside a plate cell and through a helper such as BayesianRegressionModels' `ode_rk45`, uses [diffrax](https://docs.kidger.site/diffrax/) to integrate across the requested output times. A module that solves an ODE imports `diffrax` (`pip install diffrax`); other modules do not. Emitting needs none of the Julia solver packages the native bridges load. The right-hand side `f(t, y, args...)` is translated like any helper into a nested Python function, and the extra arguments that are runtime values reach it through diffrax's `args`.

- `rk_ode_rk45_tol` is `diffrax.Dopri5()`, the Dormand–Prince 5(4) method of the native `DP5()`. `rk_ode_bdf_tol` is `diffrax.Kvaerno5()`, diffrax's stiff (L-stable implicit Runge–Kutta) method: diffrax has no BDF method, so the stiff solve uses a different method than the native `FBDF()`, with the same tolerances.
- The caller's tolerances are passed unchanged and may be traced (data or parameters). The step size follows a PID controller; outputs come from the solver's dense interpolant, so the native and JAX solves agree to the tolerances, not to the last bit.
- RK45 integrates the first derivatives of the state with respect to its initial values and floating-point right-hand-side inputs alongside the state. It scales each embedded error estimate by `abstol + reltol * max(abs(old), abs(new))` and tests the larger of two root-mean-square errors, one over state components and one over sensitivity entries. For example, `y′ = p − y` with `y(0) = p = 0` has a constant zero state. Its derivative with respect to `p` grows to `1 − exp(−100)` at time 100. The Float32 and Float64 exports recover this derivative. Value-only and differentiated evaluations both use it, so even a value-only solve can take more steps. The extra state has one column per initial-state component and floating-point input element. The tolerances control local error, and global gradient accuracy also depends on the problem and arithmetic precision.
- A solve uses the module's float type: a `float_type = Float32` module solves in float32 even with JAX's 64-bit mode on.
- When a solve runs in Float32 with a positive `reltol` below `eps(Float32)` (about `1.19e-7`), the Python module warns once and reports the requested value. For example, `reltol=1e-8` can lead to many small steps. Error control also depends on `abstol` and the state scale. For tighter relative accuracy, export with `float_type = Float64` and enable JAX x64. If the model permits a looser accuracy target, set `reltol` explicitly.
- `maxsteps` limits the accepted steps between consecutive requested outputs, as natively, and may be traced too. The static bound on attempted steps is the largest int32. Diffrax allocates checkpoint storage independently of that bound.
- On CPU, RK45 guards non-finite trials in the integration that returns the solution. For a stiff solve, a preliminary integration checks each attempted step and stops at the first non-finite candidate or error estimate. Only its status is used. If every mapped solve completes this check, the output pass uses the ordinary solver. Otherwise the batch uses the solver that isolates rejected trials from differentiation.
- For RK45, `jax.grad` contracts the integrated first variations with the output cotangent. Diffrax saves the requested initial-state and parameter columns at each output. This avoids cancellation in a long reverse pass near equilibrium. On the default CPU path, gradients of initial and output times use Diffrax's discrete adjoint with 64 checkpoints. The stiff CPU solve also uses that adjoint.
- Under `jax.vmap`, each solve uses its own step sizes. Diffrax masks lanes that finish early and chooses reverse-pass checkpoints for the whole batch. Changes in checkpoint recomputation, CUDA autotuning or a neighbour that triggers guarded retries can change gradient rounding. On a five-state, 24-cell Float64 density at tolerances `1e-8`, gradients of magnitude up to `2e3` differed by at most `2.1e-4` across neighbours or processes. Disabling XLA GPU autotuning gave bitwise agreement on that experiment.
- A ragged row of output times solves to the row's last time; its padded rows repeat that time's state, a column `sol[:, j]` keeps the padding, and reductions mask it.
- Invalid inputs (non-finite or non-increasing times, invalid tolerances or `maxsteps`) raise at run time through the module's runtime checks, as the native bridge throws. A row without output times raises nothing.
- An exceeded per-output budget and a failed solve are numerical failures, natively `ReactiveKernels.ODESolveFailure`. From a finite state, a trial with a non-finite candidate or error estimate is rejected and retried with a smaller step. Its discarded stages contribute no gradient. RK45 fails if it cannot advance to a distinct representable time. The stiff solver enforces its minimum step. Both fail for a non-finite starting state or an unusable next step. The failure is a `jax.experimental.checkify` check, which leaves every `vmap`, `scan`, `cond` and loop as a value: the functions `jax_source`'s `rejecting` names answer `-inf` for the whole evaluation, and the module's other functions raise. The module's other runtime checks are `checkify` checks too, so the first failure in program order decides, as the native program stops at its first throw: a check on a failed solve's state (a solve continuing from it) neither raises nor hides the failure. ReactiveKernelsPPL's density functions (`log_density` and its parts) are such functions, as its native sampler targets answer `-Inf`. Their gradient there is unspecified.
- A module with an ODE solve therefore needs a JAX whose `checkify` has `checkify.Error.has_error` and differentiates a `custom_vjp` (every diffrax solve) after a check. No JAX release has either yet: with jax 0.12.0.1 such a gradient is wrong or fails (`benchmark/repro_jax_checkify_custom_vjp_control_flow.py`). Branch `jax-v0.12.0.1-checkify` of [nsiccha/jax](https://github.com/nsiccha/jax) carries both, and the module refuses to import without them.

## On CUDA: one solve per lane

On a CUDA device a `rk_ode_rk45_tol` solve runs per lane in one [Pallas](https://docs.jax.dev/en/latest/pallas/) (Triton) kernel. The module selects it per platform (`jax.lax.platform_dependent`), so the same module still runs on CPU as above. Run as XLA's batched while loop, a solve paid on the GPU, per step, a round of kernel launches and a device-to-host check of the loop condition, about fifteen times per step because diffrax also loops over a step's stages, and the batch stepped until its slowest lane was done. On the density above a batched gradient so cost about 0.4 ms per step, and the card was slower than one CPU core.

- Every vmapped call (a plate's cells, a sampler's chains) joins one kernel call (`jax.custom_batching.custom_vmap`). Each lane integrates with its own step sizes. Lanes run 32 to a program, and only those 32 wait for each other.
- The kernel and Diffrax use the same first step (0.01 when representable and within the interval), Dormand–Prince tableau, state and sensitivity error test, dense output, per-output budget and retry of a non-finite trial. Rounding can change accepted steps.
- The right-hand side is traced to a jaxpr and evaluated one array element at a time, because the kernel's blocks must have power-of-two shapes. A right-hand side using a primitive this evaluation does not cover (a loop, a sort, an index at a traced position) or one Triton cannot compile in float64 (`erf`, `erfc`, `lgamma`, `digamma`, `round`) warns and uses Diffrax with forward-mode differentiation. Diffrax also handles custom derivative rules, array-valued right-hand-side arguments and vector states without explicit scalar components. It preserves the authored derivative and keeps data-sized operations as arrays.
- `jax.grad` uses forward-mode sensitivities: the kernel carries the tangents of the perturbed inputs (parameters, initial state and times) through the steps, and a custom VJP contracts them with the output's cotangent. Both backends stop gradients through the adaptive step-size factor and differentiate the same discrete update. There are no checkpoints to recompute.
- `rk_ode_bdf_tol` keeps diffrax's `Kvaerno5` on CUDA, with forward-mode sensitivities (`diffrax.ForwardMode`) instead of the checkpointed reverse pass.
- On CUDA the work per lane depends on the number of state components, right-hand-side inputs and accepted and rejected steps. A lane that reaches a large step budget can hold its kernel call for seconds. A sampler that batches chains with `vmap` also evaluates finished chains at their last state. See [Chains under `vmap`](jax-runtime.md#Chains-under-vmap).
- `RK_JAX_ODE_KERNEL` (or the module's `RK_ODE_KERNEL`) is `auto`. `off` keeps diffrax on CUDA too. `interpret` runs the CUDA path on any backend with Pallas' interpreter, as the tests do. Without `jax.experimental.pallas` the module uses diffrax.
