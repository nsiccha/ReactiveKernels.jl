ReactiveKernels.ADCostPart Type
julia
ADCostPart

One row of an ADCostProfile: a statement of the profiled program, or the time spent outside RK's generated code. name is the statement's assigned value (mu, _ppl_lik_y_resp, plate_heavy for the statement heavy of a plate cell); statements of one name are counted together. Names in parentheses group the other samples: (other statements) (code of an RK program between its assigning statements: loop control, branch conditions, calls whose result is not assigned; code of a program RK compiled for a recipe, such as a derivative rule's, counts towards the statement that calls it instead), (outside generated code) (the AD driver, DifferentiationInterface, Enzyme's runtime and the caller) and (garbage collection) (every sample inside a collection, whichever statement allocated when it started).

  • primal_seconds, gradient_seconds: the part's estimated time per call, its share of the samples times the measured time per call.

  • primal_samples, gradient_samples: the samples the estimate rests on.

  • primal_bytes, gradient_bytes: Julia heap bytes it allocated per warm call (NaN when allocations were not profiled).

  • primal_memory_seconds, gradient_memory_seconds: the part of that time spent allocating, freeing, zero-filling or copying memory in Julia's runtime or the C library: Julia heap allocation, and in the gradient also the shadows and the native malloc/free of the reverse pass's tape, which native Enzyme books on the statement whose value it stores or on the loop it stores it in.

  • callees: the functions the part's time is spent in, when the statement calls a function that is neither Julia's nor RK's own (a model's helper, a package function), each as (; name, primal_seconds, gradient_seconds), name being the function and its file, sorted by gradient time. The outermost such call counts, so a helper that calls further helpers is named itself.

ReactiveKernels.ADDerivativeReport Type
julia
ADDerivativeReport

What ad_derivative_report returns: the derivatives native Enzyme compiled, linked from a package image or ran again while the reported code ran, with ReactiveKernels' reading of their findings.

  • value: the result of the code that ran.

  • derivatives: one Enzyme.ReportedDerivative per derivative, as Enzyme reports it (enzyme-use, "What a compiled derivative calls at run time"): the differentiated function's type func, its mode, its origin, and its findings, each an Enzyme.DerivativeFinding of a call that leaves the compiled code, or nothing where Enzyme did not inspect the code.

  • unstable: derivative => finding pairs for the calls that make a derivative not type stable: a call dispatched at run time (:dynamic_dispatch), a call Enzyme differentiates at run time (:enzyme_runtime_fallback), or a box (:box).

  • allocations: derivative => finding pairs for the derivative's allocations, on Julia's heap (:gc_allocation) or native (:native_allocation, such as Enzyme's tape), with their size where it is a constant (bytes).

A finding's frames are its source lines, innermost first. In the program ReactiveKernels generates, the statement a call is in is a frame macro expansion at line 1 of the file ./rk:<value>: <value> is the value the statement assigns, the name ad_cost_profile reports (plate_<value> for a plate cell's <value>, on some loop paths with a suffix such as #direct), and (other statements) is code between statements (loop control, branch conditions, calls whose result is not assigned), such as the buffers Enzyme keeps for a plate's loop as a whole. A statement that assigns inside another is a frame inside the other's. Calls of one function in different statements are different findings, each with its own count. A finding inside a function Enzyme differentiates on its own (an in_function such as augmented_julia_copyto_…) has frames up to its call site only where that function has one call site in the derivative's code; with several, its frames end in the function itself (Enzyme snag derivative-repor-e519a164).

unstable and allocations leave out calls only reached on a path that ends in an error (throw_only), and calls an expansion of Julia's logging macros writes, which the primal check exempts too. Calls in code the derivative runs without differentiating it (sweep === :primal) count in unstable where the loaded Enzyme has the dogfood repair derivative_report_reachability, which marks the code of a function only called on an error path, such as one building an error message, throw_only (Enzyme snag derivative-repor-8d7dfce1), unless they sit in Julia's own functions (Base, Core, the standard libraries), whose bodies the primal check treats as leaves too. Without that repair unstable leaves undifferentiated code to the primal check, since error-only code would read as returning. Every other call that leaves the compiled code (:runtime_call: BLAS, Julia's runtime, separately compiled Julia code) is in derivatives only.

ReactiveKernels.NativeScheduling Type
julia
NativeScheduling(; chunk_size, workers=nothing)

Explicit native position-scheduling hints for vectorize and prepare_batched. chunk_size bounds the positions retained in each worker's output buffers. By default, the worker budget follows the Julia thread count of the process running the reader. An explicit workers sets an upper bound. Available threads and chunks cap each runtime call. Supply positive integers for these hints and choose values by measuring your workload.

One job runs its worker on the calling task. During package-image generation, two sample positions can exercise worker tasks even on one Julia thread and even when both positions fit in one chunk. With workers=1, the workload exercises the same worker inline.

For calls using several position workers, materialized data-only prefix plates also use the worker budget. Their cells share equal-input results within the call; changing data between calls recomputes the prefix. Scalar dependencies, reductions and scans retain their native order.

Ordinary batching stays serial. The schedule applies to native primal calls. Per-position AD uses the scalar kernel with prepare_ad and replica, independently of this hint.

ReactiveKernels.NonAllocatingKernel Type
julia
NonAllocatingKernel

A stateful prepared kernel whose selected single-output recipes are invoked through MutatingFunctions.apply!!. Each recipe owns a persistent typed cache: the first call seeds it and later calls offer it back for in-place reuse.

Each cache slot retains whatever its operation returned on the first call. Registered allocating operations such as copy normally seed fresh kernel-retained storage, but aliasing operations may retain caller-owned inputs, and a no-recipe plan returns its have value directly. Treat mutable results as borrowed values that may alias inputs or be overwritten by later calls. A kernel instance is therefore neither reentrant nor safe for concurrent calls; prepare one instance per independent caller.

A kernel prepared from exemplar arguments (prepare_nonallocating(spec, args...)) is typed for exactly those argument types (S, a Tuple type); calling it with arguments of other types is an ArgumentError. S is Nothing for a kernel typed by its declared HAVE port types.

ReactiveKernels.PreparationCache Type
julia
PreparationCache()

A cache of prepared kernels keyed by graph identity+version and the ordered, canonicalized have/want signature plus pass identities (gist §17). Cache lookup happens only in prepare! and in a positional call of a KernelSpec (which keeps its kernel in the graph's own cache), never inside a prepared kernel; a graph mutation bumps its version and so cannot return a stale kernel.

A bound preparation (prepare!(cache, …; bound = …)) is cached one level deeper: the planned boundary, the compiled data-only prefix and the compiled residual body are kept per graph version, have/want/pass signature and bound PORT set, so every later binding of new values to the same ports pays only the prefix's execution (the bound-data mathematics) and a fresh constant table. The entry is keyed on the PORTS, not on the bound values or their types: a later binding of differently typed data on the same ports (a different plan struct, an Int vector for a Float64 one) reuses the entry and its compiled bodies, which are generic over those types and specialize per concrete type on first use like any other Julia call; a lazy branch on a hoisted constant stays a per-call branch and follows each binding's value. An authored plate that reads a bound argument lowers for that argument's class — scalar, vector, rank-N array or tuple — as if its port declared it, so its residual is kept per class: a bound 1:n and a bound Vector domain share one, a bound scalar operand has another. Element types and extents never split it. The cache is caller-owned and grows with the distinct boundaries (and those shapes) prepared through it; it never observes the bound values afterwards and retains none of them. Rebinding is not specialized on the graph's kernel types, so a graph's first rebinding in a process compiles nothing once any graph has rebound. Lookups and first-time preparations hold the cache's lock, so one cache may serve concurrent tasks.

Plain prepare(g; …, bound) and prepare(spec; …, bound) reuse the same bound entries through a cache the graph itself holds (see prepare); a caller-owned cache gives those entries an explicit lifetime instead, independent of the graph's.

ReactiveKernels.ad_cost_profile Method
julia
ad_cost_profile(value, value_and_gradient; seconds = 1.0, threshold = nothing,
                allocations = true, min_samples = 0, max_sample_seconds = 10 * seconds) -> ADCostProfile
ad_cost_profile(prepared::PreparedADKernel, args...; kernel = prepared.kernel, kwargs...)

Measure where a prepared program's value and gradient spend their time. value and value_and_gradient are functions of no arguments that evaluate the program once (a value, then a value with its gradient, as a sampler calls them). The second form profiles kernel(args...) against ad_value_and_gradient(prepared, args...).

It first times warm calls of both and reports the ratio of the gradient's time to the value's. With threshold, it stops there unless the ratio exceeds threshold (4.0 is a usual bound for a reverse gradient), so a benchmark can call it on every program. Otherwise it runs each function for seconds under Julia's sampling profiler and attributes every sample of the calling thread to the RK statement it ran: every program RK compiles runs each statement that assigns a value in a source scope with its name, as Julia does for a macro expansion. Native Enzyme keeps those scopes in the reverse pass, so a statement's gradient time includes its reverse code inside the one fused derivative, and the parts add up to the whole. With allocations, a few further calls run under Profile.Allocs to attribute the Julia heap bytes of a warm call the same way.

The result lists parts by gradient time, each with its gradient ÷ value ratio. Estimates rest on the sample counts shown. A part with few samples is imprecise. With min_samples > 0, each pass starts with the usual seconds window. A pass with too few running samples from its calling thread continues in windows until it reaches the target or its max_sample_seconds deadline. For example, seconds=0.2, min_samples=100, max_sample_seconds=2 gives each pass up to two seconds to collect 100 samples. A call already running can finish after the deadline. The result reports the samples actually collected. Timing, resolving stack frames and allocation profiling take additional time. Profiling clears Julia's profile buffer and restores the profiler's settings afterwards. Measure on a quiet thread: the samples of other threads are ignored, but their load slows the measured one.

Time spent managing memory is reported beside the statements, because a gradient's excess over its value is often there rather than in arithmetic: each part's memory share is its time allocating, freeing, zero-filling or copying (Julia heap allocations and their shadows, and native Enzyme's tape, which it allocates with malloc and frees after the reverse pass), and every sample inside a garbage collection is counted as (garbage collection) instead of on the statement whose allocation happened to start it, which varies from run to run and host to host. The display's first lines give both shares for the whole value and gradient.

Statements in a function Julia does not inline and RK did not compile (a package function a recipe calls) count towards the RK statement that calls it, and that part's callees names the function (the display's mostly in column shows the largest when it holds at least half of the part's gradient time). Native Enzyme tapes are not Julia heap bytes; their malloc time is in memory, and Enzyme.API.printperf!(true) on the part this profile names shows what is stored.

ReactiveKernels.jax_source Method
julia
jax_source(spec::KernelSpec; have, want, types = nothing, name = :kernel,
           float_type = Float64, plate_layout = nothing) -> JAXSource
jax_source(spec::KernelSpec; have, functions, types = nothing, constants = (;),
           doc = nothing, float_type = Float64, rejecting = (), plate_layout = nothing) -> JAXSource
jax_source(p::Plan; types = nothing, name = :kernel, doc = nothing,
           float_type = Float64, plate_layout = nothing) -> JAXSource

Translate the program that computes want from have into a Python module whose function name takes the HAVE values, in order, and returns the WANT value (a tuple for several WANTs), computed with jax.numpy. With functions, a NamedTuple of function name => WANT, the module defines one function per entry over the same HAVE values; a WANT is a value name, a tuple of them (the function returns a tuple) or a NamedTuple of key => value name (it returns a dict). constants, a NamedTuple, adds module-level constants (numbers, strings, symbols, vectors, tuples, named tuples and dictionaries of these). function_docs, a NamedTuple of function name => text, gives functions their docstrings; the others state what they compute. Module functions annotate their parameters (ArrayLike) and results.

Choose plate_layout = :chains to run plate cells sequentially within an evaluation. Choose plate_layout = :rounds to batch independent subjects at the same recurrence round. With bound data, prepare_data packs variable-length vector rows by offset. A scan directly consumed by a supported subject reduction can walk all real events in one statically bounded scan. Row-local variable-length loops use Equinox for reverse-mode differentiation. Apply jax.vmap to the generated function or its gradient to batch independent parameter vectors.

jax_source reads the program in Julia's latest world, so it translates a program whose helpers, @traceable functions or kernels were defined after the calling function began, as when a function builds a program and translates it: the caller needs no Base.invokelatest.

Where a numerical method cannot produce a value at a valid input (natively a ReactiveKernels.NumericalFailure: an ODE solve that exceeds its per-output budget or fails), a module function raises, as the native program throws, except that the functions rejecting names (function names of functions, each with one WANT value) answer -inf, as a log density outside the model's support does. The failure is a jax.experimental.checkify check, which JAX carries out of every vmap, scan, cond and loop, so a plate cell's or scan step's failure rejects the whole evaluation, under jax.jit, jax.grad and jax.vmap too; a gradient there is unspecified. Only a module that can fail so wraps its functions in checkify, and its other runtime checks are checkify checks too: the first failure in program order decides, as the native program stops at its first throw, so a check on a failed solve's state (a solve continuing from it) neither raises nor hides the failure. Such a module needs a JAX whose checkify has checkify.Error.has_error and differentiates a custom_vjp (every diffrax solve) after a check. No JAX release has either yet: jax 0.12.0.1 gives a wrong or failing gradient there (benchmark/repro_jax_checkify_custom_vjp_control_flow.py). Branch jax-v0.12.0.1-checkify of https://github.com/nsiccha/jax carries both; without them, the module refuses to import.

The module docstring starts with the generated line Generated by ReactiveKernels.jax_source; do not edit. doc adds the author's description of the program after it, separated by a blank line: a string, or a Julia docstring such as @doc TOY_KERNEL (its Markdown text). A docstring written above a const binding of a kernel belongs to the binding, not to the kernel value jax_source receives, so the caller passes it. Docstrings keep their text as written: backslashes and quotes are escaped in the Python source.

types gives each HAVE value's Julia type, as a NamedTuple by port name or a tuple in HAVE order; by default the ports' declared types are used, and they must be concrete. Value ranks follow from these types, so the module is generic in array sizes: one module serves every size of the same program.

float_type (Float64, the default, or Float32) is the dtype of every float value the program does not type Float32 itself: Julia's default Float64 values, the inputs and data among them, are float32 in a module emitted with float_type = Float32, for an accelerator whose float64 is slow. Such a module casts its float inputs to float32, prepare_data returns float32 data, and the dtype metadata says so. It does not turn on JAX's 64-bit mode (jax_enable_x64) unless it rounds an fma once, which takes a float64 product. With that mode off, 64-bit integer dtypes become their 32-bit counterparts. Narrower integer dtypes keep their width and signedness. The module's floats stay float32 where another module turned x64 on. Its results carry float32 rounding: compare it with the Float64 module of the same program at a tolerance relative to eps(Float32) and the size of the value.

plate_layout = :groups (with data) emits a module whose caller chooses how plates over prepared ragged rows run: prepare_plate_layout(prepared, groups, sequential) in the module sorts each such plate's units by length and splits them into groups, each run at its own longest length side by side or one unit after another. Every layout returns the plate's values and ordinary derivatives; GROUPED_PLATES names the plates. The default :padded emits each plate as one jax.vmap over all units.

The translation keeps the program's structure. A plate is jax.vmap of its cell, a scan is jax.lax.scan of its step, a lazy branch is jax.lax.cond of its arms, and nothing is unrolled per element. Arrays keep Julia's dimension order, Julia's broadcasting rules are kept, and integer index data stay 1-based. Gradients are jax.grad of a function. A construct without a translation raises a JAXEmissionError naming its recipe.

A bounded for loop, generator, comprehension or slice over a range takes a shape-bounded number of steps, so jax.grad reverses it. Static ends and a stop that is a padded row's length have such a bound. So do ends that are entries of integer arrays of the prepared data (data): for starts[r]:stops[r], entries of two arrays at one position (also a plate cell's entries of both), it is the longest such range; for one end that is data, the largest stop less the least start. prepare_data computes these bounds and returns them with the data, under keys starting with _rk_. A range from or to an element of another such range, or of a static range (for j in i:n), is bounded by that range's ends. A step past a range's stop is a lazy branch (jax.lax.cond) that leaves the loop's values unchanged and reads nothing, so Julia's values and derivatives, empty ranges included, are kept; the work is the bound for every range, so a long range among short ones costs each of them its length. A for or while loop without a shape bound retains a runtime loop. JAX cannot reverse that loop directly; an owned derivative_rule supplies the authored reverse graph when one is available. Generators and slices still need a capacity bound for their output storage. A range known to be empty from shapes runs no JAX loop, so its body's empty-array reads are not traced.

The general partial-evaluation pre-pass. bound names the HAVE ports (as Values) whose runtime values are fixed for this binding; they must form a subset of p.have. The data-only prefix — every recipe whose transitive inputs reach only bound ports — is prepared and executed exactly once, inside this call. The result is an ordinary residual Plan whose HAVE boundary is the remaining ports, with each hoisted value re-entering as a zero-input _BoundConstant recipe, so every preparation surface consumes it unchanged and per-call work contains no data-only recomputation.

For a residual authored plate(...) do with a transparent scalar plan, named bound-only inner recipes are also evaluated at preparation. Each recipe uses only its bound inputs' broadcast coordinates, so a prefix with singleton axes is not expanded to a larger live domain. Boolean, standard 8–64-bit integer, and Float16/32/64 results needed by the residual, and dense Arrays of those element types (a per-cell index list, for example), enter as additional ordinary plate inputs; per-cell arrays are cached as an array of arrays and, like every bound or hoisted value, are shared read-only by later calls. Intermediate prefix values need only a concrete type. The original arguments remain available for shape and marker validation: their storage is retained even if the scalar residual no longer reads their elements. This trades setup and cache storage for repeated computation; inexpensive recipes need not run faster. Rebinding rebuilds these caches.

When the cell result itself reads only bound data and every other plate input is atomic (Ref), the plate's whole result is computed at preparation and replaces the plate. Its consumers that then read only bind-time values, such as reduce(vcat, cells; init = Float64[]), are computed at preparation as well, so no evaluation reads the shared hoisted storage. A cell result that is such an array but sits beside a live non-atomic input keeps its original per-cell execution: caching it would store the same shared arrays in every evaluation's output.

The inner pass retains the original plate for known empty domains. A live array whose declared type fixes its rank (whatever its element type), each of whose dimensions a bound axis of length greater than one fixes, cannot change which cells the plate visits; live numeric scalars and explicit atomic inputs do not contribute dimensions. Any other live input could make the domain smaller than the bound one, or empty, so the eligible computations run over the bound domain and the original plate is retained if any of them throws: preparation never raises an error that no evaluation of the original plate would. Their cached values serve every cell the plate visits, as they vary only along bound axes. Other exclusions are non-array/non-numeric batched bound inputs, non-concrete prefix results and overlapping inner producers. A nested plate, scan or embedded prepared kernel is never evaluated here: it stays in the residual cell, as does the producer of any data-only value that is neither such a number nor a dense Array of them (a tuple, struct, view or range); the cell's other eligible values are still cached. Ordinary recipe purity remains required. Like top-level partial evaluation, eligible computations execute eagerly at preparation over their bound domain.

A recipe, at top level or in such a cell, that reads bound and live values alike is split where its authored expression allows (_KernelSplit): each maximal strict subexpression that reads only bound data and calls more than cheap arithmetic (loggamma(n + 1.0) - loggamma(y + 1.0) beside a live logit, log(y) beside a live location) becomes a recipe of its own, computed once per binding (per lane in a cell), and the remainder reads its value. Branch arms, short-circuit operands, generators and closures are not entered, so no part runs where its expression would not; a data-bound branch arm is split after the plate partitions its lanes. The parts apply the authored operations to the same operands in the same order, so values are unchanged; nothing is algebraically simplified or reassociated.

The pass only transforms the plan: it adds no runtime wrapper and never mutates the original graph. New cached value identities use a private graph copy. Rebinding new data means running the pass again from the same original plan.

ReactiveKernels.prepare Method
julia
prepare(p::Plan; passes=(), bound=(), on_error=nothing, exemplars=nothing, type_stability=nothing, type_stability_level=nothing) -> PreparedKernel
prepare(g::Graph; have, want, passes=(), bound=(), on_error=nothing, exemplars=nothing, type_stability=nothing, type_stability_level=nothing) -> PreparedKernel

Ergonomic composition of plan -> lower -> transform -> compile. passes is a tuple of AST passes applied before compilation.

bound opts into the partial_evaluation pre-pass: pass one Value => data pair (or an iterable of them) naming HAVE ports whose runtime values are fixed for this preparation. The data-only subgraph reachable from only those ports runs once, here, and the returned kernel takes just the remaining HAVE ports positionally (in their original relative order); the hoisted values are baked in as constants. With bound = () (the default) behavior is unchanged. passes apply to the residual (per-call) kernel.

Preparing a Graph (or an authored KernelSpec) with a non-empty bound reuses everything that does not depend on the bound values — the plan, the compiled data-only prefix and the compiled residual — from earlier bindings of the same graph version, HAVE/WANT boundary, bound port set and passes, exactly as prepare! does with a PreparationCache. A binding of new values then costs the prefix's execution, not a fresh planning, lowering and compilation. The graph holds these entries, so they live as long as the graph, a mutation of the graph starts afresh, and they keep no bound values. Passes that are not singletons (closures) are not retained: such a binding is prepared afresh. A Plan is always prepared afresh.

exemplars = (x, ...) opts into native type evidence from one value per remaining positional HAVE port. Native calls then require those exact input types; prepare another kernel for different types. The native signature keeps the declared port types; only plate lowering reads the exemplar evidence. Lengths and values are not baked into the program. A graph prepared with exemplars is compiled afresh.

Preparation computes numerically fragile compositions in their stable form (simplify = true, the default): log(exp(u)) as u, log(logistic(x)) as loglogistic(x), log(1 + x) as log1p(x), y / exp(u) as y * exp(-u), log(exp(a) + exp(b)) as a log-sum-exp, and the rest of the rule table in src/stable_rewrites.jl. The literal composition is finite only where its intermediate is representable, and its ordinary reverse forms 0 * Inf at the edges; the stable form agrees with it to within rounding wherever it is finite and stays finite, with a finite derivative, beyond. Errors, lazy branches and non-Real operands keep the literal program. The rewrite applies across statements and inside plate cells, to compositions the generated program spells (recipe sources, a law's hoisted terms); it never sees inside an opaque function. simplify = false compiles the literal arithmetic; nothing takes the setting of an enclosing preparation, else the project's ReactiveKernels preference simplify (Preferences.set_preferences!(ReactiveKernels, "simplify" => false)), else true. Cached preparations are kept per setting. The same setting governs prepare_nonallocating, plate over a scalar spec, vectorize and prepare_reactive, which take simplify too, and jax_source, which reads the enclosing setting or the preference.

The same setting takes shared work out of a summed plate. When a cell's value is a + c * t, with a and c reading only values its cells share, the cells sum t alone and the plate adds n * a + c * sum(t) once: a Normal observation plate with one scale sums its squared residuals and divides by the scale once, and its ordinary reverse no longer accumulates the scale's derivative cell by cell. A law's guard on a shared value (scale == 0 before a cell's own test) is decided once per call. The plate's own loop runs instead whenever such a guard holds, a shared factor is not a normal number, or the factored sum is not finite, so every finite value and its derivatives agree with the plate's own to rounding.

With bound data and bound_statistics = true (the default, with simplify) a summed plate that sums (y - mu)^2 this way, y bound and mu linear in live values with bound coefficients, is evaluated from least-squares statistics of the bound rows computed at binding. mu may be a bound matrix times a live vector, live numbers, or live vectors gathered through one bound index, each times bound coefficients, plus bound offsets. A call then costs time in the number of parameters, not of rows, and mu is not computed; the plate's own loop, where it runs, reads it row by row. A binding whose data do not fit (fewer than two rows per parameter of a block, a non-finite entry, a response that is not a vector) compiles the plate as before. bound_statistics = false keeps the rows; nothing takes the enclosing setting (with_bound_statistics), else the project's ReactiveKernels preference bound_statistics, else true.

Selected authored plates with a single plate consumer are composed during lowering, eliminating the intermediate array. Named ports remain in p: asking for an intermediate, supplying it as HAVE, or selecting another consumer keeps that boundary. Whole-array (Ref) consumers and opaque intervening recipes also retain their materialization boundary.

Preparation checks that the program is type stable, from the declared types of the HAVE ports where those are concrete and from the bound data. How far it checks is type_stability_level:

  • :values checks that every value of the program infers a concrete type. A recipe whose inputs are concretely typed but whose result Julia does not infer concretely (Any, an abstract type, a Union, or an array of such elements), such as a call to a function whose result is not inferable, is reported, naming the value and its recipe.

  • :rk also audits the code of the prepared program: the body ReactiveKernels generates and the functions it calls from the packages of ReactiveKernels' repository (ReactiveKernels, ReactiveKernelsPPL, the other packages under packages/, and their extensions), identified by package UUID. A used value Julia does not infer concretely, or a call dispatched at run time, is reported with its method. Every other function the code calls is a leaf, whatever its package's name: its call must be dispatched statically and return a concrete type.

  • :all (the default) also audits every function that code calls, a client function's body included, except Julia's own Base, Core and standard libraries, which stay leaves.

Every recipe and plate cell that reads a non-concrete value dispatches dynamically, and native reverse-mode AD may refuse the program. prepare_ad repeats the check with the types of its exemplar arguments, auditing the callable its backend differentiates.

type_stability is what preparation does with a finding: :warn (the default) logs a warning once per process and preparation succeeds; :error throws a TypeInstabilityError naming every finding, at every preparation. Either keyword's default nothing takes the setting of an enclosing preparation, else the project's ReactiveKernels preference of the same name (read at the first preparation of a Julia session), else the default. A project sets them for every preparation, including those other packages make for it, with for example Preferences.set_preferences!(ReactiveKernels, "type_stability" => "error"), which writes [ReactiveKernels] type_stability = "error" to its LocalPreferences.toml. A keyword applies to the preparations its call makes, nested ones included, and cached preparations are kept per setting.

Prepare a reusable DifferentiationInterface gradient of the explicit scalar want port in a KernelSpec. active names one selected HAVE port or an ordered tuple of ports that remain differentiable; all other selected HAVE values are rebound on every call and passed as Constant contexts. A tuple selector is differentiated as one structured point, and gradients are returned in the same order.

The ordinary authored call surface is preserved: positional defaults and keyword HAVE ports are resolved exactly as they are by prepare(spec). The preparation arguments are type/shape exemplars, not frozen data. The backend's package must be loaded in the calling session (using Enzyme for AutoEnzyme); the backend value alone does not load DifferentiationInterface's backend extension, and preparation without it fails loudly naming the missing using.

A prepared operator serves one caller at a time, so no other thread updates the shadows its derivative accumulates into. Where the loaded Enzyme has Enzyme.set_atomic_add, a reverse-mode AutoEnzyme that leaves that setting to Enzyme (AutoEnzyme(), AutoEnzyme(; mode = Enzyme.Reverse), or the reverse part of a SecondOrder) is prepared with set_atomic_add(mode, false): plain shadow updates, where Enzyme would otherwise compile atomic ones in any process with several default-pool threads. Both keywords default to the enclosing preparation's setting or the project's preference, as for prepare. Every prepare_ad_* preparation takes the same keywords.

If the program throws at the exemplar, preparation warns and keeps the prepared operator: the check covers the derivatives that evaluation reached.

julia
rk_ode_bdf_tol(f, y0, t0, ts, reltol, abstol, maxsteps, args...)

Integrate dy/dt = f(t, y, args...) with Julia's standard OrdinaryDiffEqBDF.FBDF(), retaining one solver history across all output times. ReactiveKernels.scan Method
julia
scan(xs, ys...; init, include_init = false) do carry, x, y...
    …
    (new_carry, output)
end
scan(xs, ys...; init, history = h0) do carry, x, y..., earlier
    …
    (new_carry, output)
end

Author a bounded SEQUENTIAL recurrence inside a @kernel / @ppl body. The positionals are the sequences to scan over, advanced in lockstep (they must share axes); init seeds the threaded carry. The step reads any other enclosing value whole, as a closure. A trailing Ref(shared) operand also passes a value whole. The do-block receives (carry, x, y...) and must end with the 2-tuple (new_carry, output); scan returns the vector [output…]. A compound carry may be carried as a NamedTuple (init = (; a, b), read carry.a). Empty sequences run no step and return an empty vector of the step's inferred output type.

With the literal include_init = true, scan returns [init, output…], one element longer than the sequences and written into a single buffer: the trajectory [R₀, R₁, …, Rₙ] of a recurrence whose output is its next carry. Its value and element type (promote_type(typeof(init), output type)) are those of vcat([init], scan(…; init)) without the second vector; empty sequences return [init].

With history = h0 (a number) the do-block takes one more, last argument: the result vector being written, read-only. At step j its entry i is step i's output for i < j and h0 from j on, on every backend, so a recurrence over all earlier outputs (sum(earlier[i] * u[j - i] for i in 1:j-1; init = 0.0), with j from a lockstep eachindex(xs)) needs no carried copy of them. The result's element type is typeof(h0). A carry may not hold the history, and history cannot be combined with include_init = true.

With history = leading (a vector), the result starts with those entries: it is [leading; output…], step j writes entry length(leading) + j, and the last argument is that whole vector, with entries not written yet at zero(eltype(leading)). A recurrence seeded with a[1:m] thus reads its seeds and earlier steps from one vector.

With history = (a = leading_a, b = leading_b, ...), each named column uses the number or vector semantics above independently. The last argument and the scan result are named tuples of column vectors; the step returns a named tuple of scalar outputs with those same names. Each vector seed contributes its own prefix, and each column retains its seed's element type.

It lowers to one retained ordered loop, so a natural sequential recurrence needs no closed-form rewrite. This is @kernel authoring sugar recognized by the macro as a recipe's right-hand side, like an authored plate; it is not a callable runtime function outside a kernel body.

ReactiveKernels.@kernel Macro
julia
@kernel model(f, x) = begin
    y = f(x)
end

kernel = prepare(model)
kernel(sin, 1.0)

@kernel affine(x, scale = 2; offset = scale - 1) = begin
    y = scale * x + offset
end

prepare(affine)(3; offset = 4)

@kernel square(x) = x * x

prepare(square)(3)

@kernel begin
    x::Float64
    y::Float64 = f(x)
    return y
end

Build a named KernelSpec without executing any recipe RHS. The primary form mirrors an ordinary Julia function definition: its signature names the default have ports, including function-valued inputs. The macro binds the function name to the resulting KernelSpec; prepare turns it into the callable straight-line kernel. Both short and long definitions are supported. Trailing positional defaults and fixed keyword arguments use ordinary Julia call syntax. Defaults are evaluated at call time, from left to right, and may refer to earlier positional or keyword arguments. A keyword without a default is required. Defaulted and keyword arguments remain exposed have ports; the signature adapter only fills their values before entering the same generated positional kernel. Variadic positional and keyword splats are not supported.

Type annotations are optional metadata. Omitting them does not add dynamic dispatch to a prepared kernel: Julia specializes the generated function on the concrete operation and input types at the call site. An assignment creates one recipe; tuple assignment creates a multi-output recipe, and assigning an output again creates an alternative producer. Declarations and producers may be forward-referenced: the complete named-port namespace is collected before dependencies are inferred. When a caller global has the same name as a port, qualify the global with its module name.

Every signature argument and assignment is exposed by name. return is optional: without one, derived sink ports form the default want boundary; with one, the returned port names replace that default. Either way, every port remains selectable through spec[:name] or want = :name.

A direct call to another stateless KernelSpec on a recipe RHS splices that kernel's recipes into this graph during construction. Pass existing typed ports positionally and destructure the nested default output boundary exactly. Every call site receives fresh internal value identities, so repeated calls remain independent while the outer planner can prune or CSE their recipes. No nested runtime call remains in a prepared kernel.

Calling a spec itself with positional values, spec(args...), runs its default boundary, as prepare(spec)(args...) does. The graph keeps that prepared kernel, so only the first call per graph version prepares it (and the first under another preparation setting, such as simplify); later calls cost a cache lookup on top of the kernel's own call. A hot loop that holds prepare(spec) skips the lookup as well.

A short expression body is a compact single-result kernel. Its value is exposed as a port named after the kernel, and that port is the default want boundary: @kernel square(x) = x * x creates ports :x and :square. A bare identity such as @kernel passthrough(x) = x aliases the result port directly to the input without an identity recipe or an additional physical slot. Block bodies retain the graph-oriented sink/explicit-return behavior described above.

Recipe metadata uses the compact form

@recipe (cost = 1.2, cse_key = :combined) (a::T, b::T) = combined(u)

All recipe bodies resolve and capture names in the caller's scope. The macro only constructs closures and graph metadata; recipe bodies run only when a prepared kernel is invoked.

@kernel supports two authoring modes, discriminated by the body. A methodless recipe body authors a stateless graph KernelSpec — this docstring's primary form. A body with nested method definitions authors an OBJECT kernel with an IMPLICIT synthesized receiver: pure straight-line methods are transparent named endpoints. Nested methods declare no self/__self__ formal, bare unshadowed names are the owner's fields, and __self__ appears only as a sibling object-pass actual (flip!(__self__, depth)). ReactiveKernels compiles pure kernels only: a methodless body that mutates a field of its first positional subject, or any !! name (a strong same-object update such as nuts!!(state; rng)), is a stateful free method and raises an ArgumentError. Reactive mutation of a compiled stateless kernel remains available through prepare_reactive, set!, mutate!, and touch!.
